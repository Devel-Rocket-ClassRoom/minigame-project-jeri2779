## 2. 무기 시스템 설계 방향 (4일차 확정)

### IWeapon 인터페이스 도입 이유
- 총기 / 근접 / 투척이 공유하는 것은 `TryFire()` 행동 하나
- 공통 필드가 거의 없으므로 상속보다 인터페이스가 더 가벼움
- `CharacterCombat`은 `IWeapon`만 바라보며 뒤에 어떤 구현체가 붙어도 무관

```csharp
public interface IWeapon
{
    bool TryFire();
    void TryReload();
    WeaponData Data { get; }
}
```

### 무기 종류별 구현 분리 이유
- 총기: ammo 체크 → 머즐플래시 → true/false 반환
- 근접: OverlapSphere → 범위 내 적 데미지 (Raycast 없음)
- 투척: 투사체 Instantiate → 물리 발사 (지연 데미지)
- **무기 추가 시 해당 스크립트만 작성, 기존 코드 수정 없음**

### CharacterCombat 역할
- 입력 수신 → `inventory.CurrentWeapon.TryFire()` 호출
- 총기 성공 시: Raycast → 헤드샷 판정 → 데미지 계산 → `IDamageable.TakeDamage()`
- 반동: `CharacterMoves.AddRecoil()` 호출
- 근접/투척은 `TryFire()` 내부에서 데미지까지 자체 처리

### WeaponInventory 4슬롯 구조
```
슬롯 0 (1키) — Primary   (주무기, AR 등)
슬롯 1 (2키) — Secondary (보조무기, 권총 등)
슬롯 2 (3키) — Melee     (근접)
슬롯 3 (4키) — Throwable (투척)
```
- 상점 구매 시: 같은 카테고리 슬롯에 교체 (기존 인스턴스 파괴, 새 프리팹 Instantiate)
- WeaponCategory enum으로 슬롯-카테고리 매핑

## 3. 적 시스템 설계 방향 (4일차 확정)

### EnemyBase 상속 구조 도입 이유
- HP, NavMeshAgent, FSM(Chase/Dead 등) 공통 필드가 많음
- 공통 필드가 많으므로 인터페이스보다 상속이 적합
- `Attack()`만 override, 나머지 FSM 흐름은 부모가 처리

```
EnemyBase (공통 FSM + 필드)
    ├─ MeleeEnemy  : override Attack() → 근접 콜라이더
    ├─ ChargeEnemy : override Attack() → 돌진 (ChargeReady/Charge 상태 추가)
    └─ RangedEnemy : override Attack() → 투사체
```

- **적 추가 시 자식 클래스만 작성, EnemyBase 수정 없음**
- 현재 `EnemyController.cs`가 `EnemyBase`로 전환되는 구조

## 6. 주의사항
